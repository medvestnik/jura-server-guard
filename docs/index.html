Overview

Что такое Jura Server Guard

Jura Server Guard — лёгкая локальная панель безопасности для серверов с PHP-сайтами. Она помогает быстро увидеть пользователей и сайты под /var/www, запустить проверку, разобрать подозрительные файлы и сохранить доказательства для инцидент-репонса.

Что обнаруживает

  • подозрительные PHP-файлы и webshell-маркеры;
  • packed loaders, eval, gzuncompress, gzinflate и self-reading payloads;
  • SEO cloaking, ALFA/alfacgiapi-индикаторы;
  • fake validation folders: well-known, pki-validation, PHP внутри validation paths.

Что поддерживает

  • карантин и восстановление подозрительных файлов;
  • профили сканирования fast, standard, deep;
  • Telegram-уведомления о критичных находках;
  • host-level мониторинг SSH-ключей, cron и процессов;
  • браузер и selective restore из ISPmanager/custom backups.
Info. Инструмент не заменяет полноценный EDR/антивирус. Его задача — дать хостинг-администратору быстрый обзор PHP-сайтов, подозрительных изменений, host-level persistence points и безопасный workflow карантина.

Installation

Установка

Рекомендуемая схема — хранить рабочую копию репозитория в /root/jura-server-guard, а установленное приложение в /opt/jura-server-guard. Для запуска используйте альтернативный PHP, например /opt/php83/bin/php.

Warning. Не заменяйте системный PHP на ISPmanager/AlmaLinux сервере. Панель должна работать с выбранным бинарником PHP, например /opt/php83/bin/php, без переключения системного /usr/bin/php.
Recommended PHP/opt/php83/bin/php
Repo path/root/jura-server-guard
Install path/opt/jura-server-guard
Servicejura-server-guard
Timerjura-server-guard-scan.timer
Panel bind127.0.0.1:8765
cd /root/jura-server-guard
sudo JURA_PHP_BIN=/opt/php83/bin/php bin/install-almalinux.sh

После установки проверьте сервис, таймер и порт:

systemctl status jura-server-guard --no-pager -l
systemctl status jura-server-guard-scan.timer --no-pager -l
ss -lntp | grep 8765

Для production-сервера после базовой установки рекомендуется сразу настроить Telegram и включить host-level мониторы:

cd /opt/jura-server-guard
# сначала заполните JURA_TELEGRAM_* в .env и проверьте отправку
/opt/php83/bin/php artisan guard:telegram-test --message="Jura Server Guard Telegram test"

# затем установите systemd-мониторы SSH-ключей, cron и процессов
sudo bash bin/install-security-monitors.sh

Telegram alerts

Подключение Telegram-уведомлений

Telegram используется scanner-уведомлениями, монитором SSH-ключей, монитором cron и монитором подозрительных процессов.

  1. Откройте в Telegram @BotFather и выполните /newbot.
  2. Скопируйте токен бота в /opt/jura-server-guard/.env.
  3. Напишите любое сообщение новому боту от аккаунта или группы, куда должны приходить уведомления.
  4. Откройте https://api.telegram.org/bot<TOKEN>/getUpdates и найдите message.chat.id.
  5. Для групп chat id часто отрицательный, например -1001234567890.
JURA_TELEGRAM_ENABLED=true
JURA_TELEGRAM_BOT_TOKEN=123456789:telegram-bot-token
JURA_TELEGRAM_CHAT_ID=123456789
cd /opt/jura-server-guard
/opt/php83/bin/php artisan guard:telegram-test --message="Jura Server Guard Telegram test"
Tip. Если getUpdates возвращает пустой результат, отправьте боту ещё одно сообщение и обновите URL. Если бот используется в группе, сначала добавьте бота в группу и только потом проверяйте getUpdates.

Host security monitors

Мониторинг SSH-ключей, cron и процессов

Host-level мониторы отслеживают точки закрепления, которые часто используются после взлома сервера: добавление SSH-ключей, пользовательские и системные cron-задания, подозрительные процессы из временных директорий.

SSH authorized_keys

Следит за /root/.ssh/authorized_keys и /var/www/*/data/.ssh/authorized_keys. При появлении нового fingerprint отправляет Telegram-уведомление с host, файлом, строкой, типом ключа, SHA256 fingerprint, comment и mtime.

User/system cron

Следит за /var/spool/cron/*, /etc/crontab, /etc/cron.d/* и стандартными каталогами /etc/cron.*. Уведомляет о новом cron-файле, изменении hash или новой non-comment строке.

Suspicious processes

Сканирует /proc и уведомляет о новых подозрительных сигнатурах процессов: deleted executable, запуск из /tmp, /dev/shm, bin-tmp, mod-tmp, gs-dbus, kdevtmpfsi, xmrig, curl|wget | sh и encoded/eval shell patterns.

Установка создаёт baseline без Telegram-шума по уже существующим ключам, cron-заданиям и процессам, затем включает systemd units:

cd /opt/jura-server-guard
sudo bash bin/install-security-monitors.sh
jura-server-guard-ssh-keys.path      # immediate authorized_keys watch
jura-server-guard-user-cron.timer    # every minute
jura-server-guard-processes.timer    # every minute

Проверка статуса:

systemctl status jura-server-guard-ssh-keys.path --no-pager
systemctl list-timers | grep jura-server-guard
journalctl -u jura-server-guard-ssh-keys.service -n 50 --no-pager
journalctl -u jura-server-guard-user-cron.service -n 50 --no-pager
journalctl -u jura-server-guard-processes.service -n 50 --no-pager

Ручные проверки:

cd /opt/jura-server-guard
/opt/php83/bin/php bin/ssh-key-monitor.php
/opt/php83/bin/php bin/user-cron-monitor.php
/opt/php83/bin/php bin/process-monitor.php --dry-run

Основные настройки в .env:

JURA_SSH_KEY_MONITOR_FILES=/root/.ssh/authorized_keys,/var/www/*/data/.ssh/authorized_keys
JURA_USER_CRON_MONITOR_FILES=/var/spool/cron/*,/var/spool/cron/crontabs/*,/etc/crontab,/etc/cron.d/*,/etc/cron.hourly/*,/etc/cron.daily/*,/etc/cron.weekly/*,/etc/cron.monthly/*
JURA_PROCESS_MONITOR_IGNORE_REGEX=
Info. Детальная документация по host-level мониторингу вынесена в SECURITY_MONITORS.md, отдельно по SSH-ключам — в ssh-key-monitor.md.

Accessing the panel

Доступ к web-панели

Панель должна слушать только localhost на сервере. Для удалённой работы откройте SSH-туннель с вашей рабочей машины:

ssh -p 22222 -L 8765:127.0.0.1:8765 root@SERVER_IP

Затем откройте в браузере:

http://127.0.0.1:8765
Danger. Не публикуйте порт 8765 в интернет. Даже при наличии логина панель управляет сканированием, просмотром файлов, карантином и потенциальным restore. Доступ должен идти через SSH-туннель, VPN или другой закрытый административный контур.

Количество системных пользователей с сайтами в /var/www/{user}/data/www. Помогает оценить охват инвентаризации.

Количество найденных сайтов. Из карточки удобно перейти к скану конкретного сайта.

Last scan

Последний запуск: профиль, статус, длительность, количество файлов и находок.

Scan history

История ручных и timer-сканов с областью проверки: all sites, user или site.

Recent suspicious log events

Свежие подозрительные HTTP-события из access/error логов с URI, IP и raw details.

Scan profiles

Профили сканирования

fast

Профиль по умолчанию для timer и dashboard. Проверяет PHP/config/dangerous directories, validation paths, uploads PHP, плагины и темы. Пропускает обычные media/images и подходит для ежедневного мониторинга.

standard

Сбалансированный ручной скан. Добавляет больше типов файлов, suspicious media, JS/HTML и content mismatch проверки. Хорош для расследования без полного обхода всех архивов и медиа.

deep

Полный аудит вручную. Включает media, archives, polyglot checks и тяжёлые проверки. Не используйте как timer-профиль на больших production-сайтах.

/opt/php83/bin/php artisan guard:scan --profile=fast
/opt/php83/bin/php artisan guard:scan-site /var/www/zao/data/www/zaodessu.com.ua --profile=fast --verbose
/opt/php83/bin/php artisan guard:scan-user zao --profile=standard

Running scans from the web panel

Запуск сканов из панели

В панели доступны кнопки запуска скана на разных уровнях:

  • Dashboard scan buttons — быстрый scan всех сайтов, обычно fast.
  • Site scan button — проверка одного сайта, когда есть конкретный URI или finding.
  • User scan button — проверка всех сайтов одного пользователя ISPmanager.
  • Profile dropdown — выбор fast, standard или deep перед запуском.
  • Active scan/progress — отображение текущей операции, статуса, прогресса и результата.
Info. Concurrent scans ограничены глобальным lock-файлом и статусом running scans. Это защищает сервер от перегрузки диска/CPU и предотвращает конфликтующие изменения в истории файлов и findings.

Findings

Находки и их разбор

Finding — это подозрительный файл, изменение или событие, подтверждённое правилом сканера. Начинайте с critical/high, затем разбирайте medium и low.

Risk levels

  • critical — webshell, packed loader, ALFA markers, PHP в validation directory.
  • high — сильные malware-индикаторы, risky upload PHP, подозрительный POST к файлу.
  • medium — подозрительное имя/путь/комбинация функций.
  • low — слабый сигнал или allowlisted файл с изменениями.

Finding status

  • new — новая находка, ещё не разобрана.
  • open — подтверждена и находится в работе.
  • quarantined — файл перемещён в карантин.
  • restored — восстановлен из quarantine/backup.
  • ignored / false positive — можно использовать, если реализовано в текущей версии.

На странице finding detail проверяйте evidence и matched rules, а также технические атрибуты: sha256, размер, mtime, owner, group и permissions. Эти данные нужны для отчёта и для сравнения с backup.

Quarantine and restore

Карантин и восстановление

Безопасный workflow: не удаляйте подозрительный файл сразу. Сначала сохраните evidence, переместите файл в quarantine и только затем восстанавливайте чистую версию из backup или CMS checksums.

  1. Откройте finding detail и проверьте matched rules.
  2. Сохраните stat, sha256, путь и raw evidence.
  3. Переместите файл в quarantine.
  4. Проверьте сайт и логи.
  5. Restore из quarantine выполняйте только для false positive.
Warning. Web actions могут быть отключены по умолчанию. Это нормальная безопасная настройка: destructive операции лучше выполнять осознанно через CLI или включать web actions только на время администрирования.
/opt/php83/bin/php artisan guard:quarantine FINDING_ID
/opt/php83/bin/php artisan guard:restore QUARANTINE_ID

ISPmanager backup integration

Интеграция с ISPmanager backups

Настройки находятся в Settings → Backups. Включите backup integration и выберите provider:

  • ISPmanager — стандартная структура backups.
  • Custom backup folder — пользовательский backup root.
  • Disabled — интеграция скрыта и не используется.

Default backup root: /var/backup. Путь можно изменить в настройках. Типичная структура ISPmanager:

/var/backup/{user}/{date}/
Warning. Differential/incremental backups могут зависеть от цепочки архивов. Для полного восстановления сайта используйте штатные средства ISPmanager; Jura Server Guard ориентирован на безопасный selective restore отдельных файлов.

Workflow: найдите файл в backup, откройте preview нужной версии, сравните Diff current vs backup, затем восстановите только выбранный файл. Web restore отключён по умолчанию, пока администратор явно не включит эту возможность.

Incident response

Типовые сценарии реагирования

Scenario A: fake WordPress files на DLE-сайте

Если на DLE-сайте найден wp-blog-header.php, это сильный сигнал подмены или попытки замаскировать malware под WordPress. Проверьте finding, отправьте подозрительные файлы в quarantine, затем восстановите index.php и .htaccess из чистого backup.

Scenario B: fake well-known folder

Реальный ACME path — .well-known с точкой. Каталог well-known без точки подозрителен. PHP-файлы внутри validation directories считаются critical: отправьте их в quarantine или удалите fake folder после сохранения evidence.

Scenario C: packed PHP loader

Критическая комбинация: self-reading file file_get_contents(__FILE__), распаковка через gzuncompress/gzinflate, eval и appended binary/compressed payload. Такие файлы сначала карантинируйте, затем ищите точку загрузки и соседние backdoors.

Scenario D: false positive в легитимных WordPress files

Если файл похож на legitimate WordPress core/plugin, проверьте checksums перед карантином:

wp core verify-checksums --path=/path/to/site --allow-root
wp plugin verify-checksums plugin-slug --path=/path/to/site --allow-root

Updating

Обновление Jura Server Guard

Перед обновлением остановите timer и сервис, подтяните репозиторий, синхронизируйте код в /opt/jura-server-guard, примените миграции и запустите сервис. Если обновление добавляет host-level monitors, после синхронизации запустите bin/install-security-monitors.sh.

systemctl stop jura-server-guard-scan.timer jura-server-guard-logs.timer
systemctl stop jura-server-guard

cd /root/jura-server-guard
git fetch --all --prune
git pull --ff-only

rsync -a --delete \
  --exclude='.env' \
  --exclude='storage/' \
  --exclude='vendor/' \
  /root/jura-server-guard/ /opt/jura-server-guard/

cd /opt/jura-server-guard
/opt/php83/bin/php artisan migrate

# Если добавлены или изменены параметры .env, отредактируйте .env и примените их:
/opt/php83/bin/php artisan config:cache

# install/update host-level systemd monitors: SSH keys, user cron, suspicious processes
sudo bash bin/install-security-monitors.sh
# переустановить unit-файлы, включить и перезапустить оба таймера
sudo bash bin/install-scan-timers.sh

systemctl status jura-server-guard --no-pager -l
systemctl status jura-server-guard-scan.timer --no-pager -l
systemctl status jura-server-guard-logs.timer --no-pager -l
systemctl status jura-server-guard-ssh-keys.path --no-pager
systemctl list-timers | grep jura-server-guard
Tip. Если composer.json и composer.lock не изменились, Composer можно пропустить. Если Composer нужен, определяйте доступный composer или composer.phar на сервере; не полагайтесь на жёсткий путь /root/jura-server-guard/composer.phar.

Troubleshooting

Диагностика проблем

Частые причины

  • panel not opening — нет SSH tunnel или сервис не запущен;
  • port 8765 not listening — упал jura-server-guard или bind изменён;
  • scan lock stuck — предыдущий scan аварийно завершился;
  • SQL missing column after update — не выполнен artisan migrate;
  • timer accidentally running — timer не остановлен перед ручным обслуживанием;
  • host monitor alerts not delivered — не заполнены JURA_TELEGRAM_* или не запущены systemd units;
  • too many findings — запущен deep на большом сайте;
  • false positives — проверьте CMS checksums и allowlist.

Полезные команды

systemctl enable --now jura-server-guard.service
systemctl status jura-server-guard.service --no-pager -l
journalctl -u jura-server-guard.service -n 100 --no-pager
systemctl cat jura-server-guard.service
ss -lntp | grep ':8765' || true
ps aux | grep '[a]rtisan guard:scan'
/opt/php83/bin/php artisan guard:scan-unlock --force
/opt/php83/bin/php artisan guard:cleanup-running-scans
systemctl status jura-server-guard-ssh-keys.path --no-pager
journalctl -u jura-server-guard-processes.service -n 50 --no-pager

Панель не открывается после обновления

Ошибка SSH-туннеля open failed: connect failed: Connection refused означает, что SSH работает, но сервер не слушает 127.0.0.1:8765. После проверки статуса и журнала можно отдельно проверить запуск приложения:

cd /opt/jura-server-guard
/opt/php83/bin/php artisan serve --host=127.0.0.1 --port=8765

# Если прямой запуск успешен, остановите его через Ctrl+C:
systemctl restart jura-server-guard.service
systemctl status jura-server-guard.service --no-pager -l
ss -ltnp | grep ':8765' || true

Security recommendations

Рекомендации по безопасности

  • Держите панель привязанной к 127.0.0.1.
  • Используйте SSH tunnel для доступа.
  • Включите Telegram и host-level monitors после установки.
  • Отслеживайте authorized_keys, cron и подозрительные процессы через systemd units.
  • Держите web restore отключённым, пока он действительно не нужен.
  • Не выполняйте массовый quarantine для medium findings без ручной проверки.
  • Проверяйте checksums WordPress core/plugins перед выводом о заражении.
  • Используйте backups перед заменой файлов.
  • Сохраняйте evidence: stat, sha256, quarantine path, matched rules, raw log и host-monitor alert.
